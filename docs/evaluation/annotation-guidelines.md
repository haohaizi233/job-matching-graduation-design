# 人工标注操作细则（`phase4-3a-annotation-v1`）

配套协议：[`phase4-3a-protocol.md`](phase4-3a-protocol.md)。
本细则是标注员的**唯一操作依据**；与协议冲突时以协议为准并上报。

## 一、标注员与盲标纪律

1. 每条样本由**两名标注员独立作答**，互相不可见对方答案。
2. 标注文件中**不得**包含任何模型预测分数、旧系统评分（`final_score`、
   `label_strength`、`candidate_rank` 等）。见到此类列立即停止并上报，不得据此判断。
3. 不得与被评模型开发者讨论具体样本的"标准答案"。
4. 每条记录必须留 `reason`（判定依据编号）与 `evidence`（原文片段），
   无证据的标注视为无效。
5. 联系方式、姓名、住址等个人信息在 `evidence` 中必须以 `***` 替代（脱敏）。

## 二、填写字段

| 字段 | 填写要求 |
|---|---|
| `annotator_id` | 工号/署名，例 `annotator_A`；不得填模型名或 `auto`/`llm` |
| `pair_id` | 抄写样本表中的配对 ID，不得改动 |
| `relevance` | `0` / `1` / `2` / `unjudgeable`（四选一） |
| `confidence` | `high` / `medium` / `low` |
| `reason` | 依据编号 + 一句话理由，例：`1,3 必备技能 Python/SQL 均满足，学历本科符合` |
| `evidence` | 引用简历/JD 原文片段（每条 10–60 字），多个片段用 `；` 分隔 |
| `annotation_timestamp` | ISO 8601，例 `2026-10-29T10:00:00` |
| `protocol_version` | 固定填 `phase4-3a-annotation-v1` |

依据编号：`1` 必备技能；`2` 职责-经历关联；`3` 学历/毕业届别等资格；
`4` 工作经验年限与方向；`5` 核心技术方向一致性。

## 三、三级标签判定标准

### `2` 高度匹配

同时满足：

- 必备技能（`required_skills`）**大部分**满足（≥ 70% 且核心技能不缺）；
- 简历项目/工作经历与岗位职责**直接对应**（做过同类事情，不是"了解"）；
- 学历、经验等硬性条件**全部**满足；
- 核心技术/业务方向一致。

### `1` 部分匹配

- 必备技能部分满足（约 30%–70%），或核心技能缺 1 项；
- 职责有交集但覆盖不全 / 层级不同（如要求 3 年经验、简历 1 年）；
- **或**硬性条件（学历、经验、方向）有 1 项不满足（此时无论技能多高，上限即为 1）。

### `0` 明显不匹配

- 必备技能基本不满足（< 30%）**且**职责无对应经历；
- 或岗位核心方向与简历方向完全不同（如财务岗 ↔ 算法工程经历）；
- 且**证据充分**（不是"没写"，而是"写了且对不上"）。

### `unjudgeable` 资料不足

- 简历关键部分缺失（无项目/经历描述、无技能信息）导致无法比对；
- JD 关键部分缺失（无职责、无要求）；
- 信息自相矛盾且无法判断以哪个为准；
- 文本为外语/乱码/截断导致无法理解。

**关键纪律**：`简历没写 ≠ 不满足`。
「简历未提及某技能」若简历整体信息完整，应按「不满足」处理（计入 0/1 的判断）；
若简历本身信息不足以判断，才允许 `unjudgeable`。禁止把信息缺失一律判 0。

## 四、常见陷阱

| 场景 | 错误做法 | 正确做法 |
|---|---|---|
| 技能关键词命中多但职责完全不同 | 判 2 | 按职责-经历关联降级，多为 1 |
| 岗位要求「本科及以上」，简历大专 | 因技能好判 2 | 硬条件不满足，上限 1 |
| 简历缺少项目描述 | 判 0 | `unjudgeable`（信息不足） |
| 城市不同 / 薪资期望不匹配 | 写进 relevance | 不进入 relevance，单独记录过滤维度 |
| 岗位写着「学历不限」 | 担心不真实判 unjudgeable | 按字面判定资格维度即可 |
| 合成测试池样本 | 随手标 2 | 正常标注，但该样本永远不进入正式真值 |

## 五、仲裁规则（仲裁员）

1. 只仲裁两人 `relevance` 不一致的样本（含 `unjudgeable` vs 0/1/2）。
2. 仲裁员必须独立看原文，可以参考两份 `reason`/`evidence`，但不得直接取平均。
3. 仲裁记录字段：`arbitrator_id`、`pair_id`、`final_relevance`、`final_confidence`、
   `reason`、`evidence`、`annotation_timestamp`、`protocol_version`。
4. 仲裁结论若为 `unjudgeable`，最终标签即 `unjudgeable`，不得强行归入 0/1/2。
5. 原始两份标注**永久保留**，仲裁不得覆盖。

## 六、质量检查（导入时自动执行）

- 标签值合法、`pair_id` 存在、`annotator_id` 已登记；
- 同一标注员对同一样本只有一条有效记录（重复冲突直接拒收）；
- `unjudgeable` 样本不得被强行归类；
- 标注文件不得包含模型输出列；
- 全表 `protocol_version` 一致。

一致性指标（原始一致率、Cohen's Kappa、Weighted Kappa）由
`scripts/phase4_3a/check_agreement.py` 计算；样本不足时输出
`not_computable` 与原因，不填充任何数值。
